# リリース前 手動確認チェックリスト

E2E (`npm run e2e`) は「拡張が読み込まれ、IN で範囲ができ、ページ内で録画を始められる
状態になる」という、**IN による範囲確定まで**しか自動化していない。実際の
録画・プレビュー・X への添付は、録画そのものが実時間かかる、耳や目で確認
するしかないもの、ログイン済みアカウントが要るものを含め、すべてこの
チェックリストで手動確認する。X への添付はログイン済みアカウントを必要と
するため、認証情報をテストに持たせない方針であえて自動化していない。

## 準備

1. `npm run build`
2. `chrome://extensions` を開き、デベロッパーモードを有効にする
3. 「パッケージ化されていない拡張機能を読み込む」で `dist/` を指定する
4. X にログインしておく

## 最初に確認すること (ここが通らないと以降は意味を持たない)

- [ ] **録画された動画に、コメント欄やプレイヤーの操作系が映っていない。** 動画の中身だけが録れていること
- [ ] **録画データが実際に保存されているか。** 1 本録って保存されたファイルが再生でき、DevTools の Application → IndexedDB → `yt-clip` → `clips` で Blob のサイズが妥当（数百 KB 以上）であること。**数バイト〜数十バイトなら転送が壊れている**
- [ ] **ツールバーを経由せず、YouTube のページから直接録画を開始できる。** 権限エラーが出ないこと
- [ ] **正常な録画・投稿が「録画対象のタブが見つかりません」(`tab-lost`) やダウンロード誘導に化けないか。** service worker はタブへの指示 (`recorder/start` / `recorder/stop` / `x/payload`) の結果を待つが、**失敗に落とすのは「受け手が居ない」と分かったときだけ**で、応答が無いだけ (5 秒でタイムアウト) なら続行する。ここが逆に解釈されると、正常な録画がすべて止まるか、添付が済んでいるのに popup がダウンロード誘導になる。**最初に 1 本通しで録って投稿まで確認する**
- [ ] **60 秒いっぱい・1080p のクリップが X に添付できるか。** 動画は base64 にして 2 回運ばれる（content → service worker → 投稿タブ）。大きいクリップだけ失敗する可能性がある。添付されたファイルのサイズが元と一致することも確認する。**失敗した場合は、無反応にならず YouTube ページのバーに「拡張への送信に失敗しました: …」が出て、popup が「録画が中断されました」(failed) へ抜けること**

## 通常フロー (MP4 対応環境)

### 範囲の指定

- [ ] **IN を押すまで拡大バーは操作できない。** バーはプレイヤーの下に薄く表示されているが、ハンドルをドラッグしても動かないこと (spec §5.3 のとおり、範囲が確定するまで操作させない)
- [ ] IN を押すと 15 秒の範囲ができ、拡大バーのハンドルが操作できるようになる
- [ ] YouTube のシークバーに、範囲が帯で重なって見える
- [ ] **1 時間以上の動画で、拡大バーのハンドルが秒単位で動かせる**
- [ ] ハンドルをドラッグすると、動画がその位置に追従する
- [ ] ハンドルが窓の端で止まり、それ以上動かない
- [ ] 範囲を 1 秒未満にしようとすると、そこで止まる
- [ ] 範囲を 60 秒より長くしようとすると、そこで止まる
- [ ] 「範囲を再生」で IN から OUT まで再生され、OUT で止まる
- [ ] 録画中は IN / OUT / ハンドルのいずれも操作できない
- [ ] **録画後 (popup が「録画できました」= preview) もハンドルが操作できない。** 状態機械はこの状態の範囲変更を拒むため、動かせてしまうと画面と状態が食い違う

### 録画〜投稿

- [ ] 「録画」を押すと開始位置へ移動し、そこから再生が始まる
- [ ] **クリップの冒頭が欠けていない** (IN で指定した位置から始まっている)
- [ ] OUT の位置で録画が止まり、末尾が伸びていない
- [ ] 自動保存されたファイルを開いて内容を確認できる
- [ ] 「取り直し」で同じ範囲を録り直せる
- [ ] 「X に投稿」で投稿画面が開き、動画が添付される
- [ ] 本文にタイトルと開始秒つき URL が入っている
- [ ] **投稿ボタンが自動で押されていない**
- [ ] 実際に投稿して、X 上で動画がインライン再生される

## 拡大バーの操作 (詳細)

単体テストでは座標計算しか固めておらず、実際に触れるかどうかは実機でしか
分からない項目。

- [ ] `getBoundingClientRect().width <= 0` の**実発生条件** (シアターモード切替・フルスクリーン遷移) を再現し、そのときハンドルが窓の先頭へ飛ぶような見た目のジャンプが起きないか確認する
- [ ] `setPointerCapture` / `pointercancel` の実挙動 (ドラッグ中にタブを切り替える・システム通知が割り込む) を確認する。ドラッグが中途半端な状態で固まらないこと
- [ ] CSS 変数フォールバック色の**視認性** (ライト / ダーク双方の YouTube テーマで)。拡大バーのハンドルや選択範囲の色が背景に埋もれていないこと

## 制約の確認

- [ ] **OUT ボタンで範囲を確定させたとき、60 秒を超える／1 秒未満だとエラー文言が出て録画に進めない。** (例: IN の 70 秒後で OUT を押すと「クリップは 60 秒までです (現在 70 秒)」、IN の直後で OUT を押すと「クリップは 1 秒以上必要です」が出る。) **これは拡大バーのハンドルをドラッグしたときに黙って端で止まるクランプ挙動 (`clampHandle`) とは別の経路で、`onMarkOut` → `validateRange` (`src/content/youtube.ts` / `src/shared/time.ts`) を通る。ハンドル操作だけを確認してこの項目を省略しないこと**
- [ ] **X に未ログインの状態で「X に投稿」を押したとき、操作不能にならないか。** 投稿画面ではなくログイン画面が開くため添付は完了しない。バーに「取り直す」が出ていて、そこから抜けられること（service worker は数十秒で止まるため、時間切れによる自動退避は当てにできない）
- [ ] **投稿画面が開いた直後にそのタブを閉じたとき、操作不能にならないか。** 同じくバーの「取り直す」から抜けられること
- [ ] 広告の再生中に録画しようとすると中断され、理由が表示される
- [ ] **録画中 (seeking / recording / encoding のいずれか) に対象の YouTube タブを閉じると、バーに「録画対象のタブが見つかりません」が出て「再試行」が押せる。** タブを閉じ、同じ動画を開き直して確認する (`chrome.tabs.onRemoved` 経由。service worker は数十秒で止まるためタイマーによる退避は当てにできない)

## degraded path

- [ ] MP4 非対応の環境で「この環境では X に直接添付できません」と表示される
- [ ] その状態でも WebM が自動保存される (保存されたファイルの拡張子が `.webm` であること。MIME からパラメータを落としても `video/webm` の判定が効いていること)
- [ ] X の添付に失敗しても、バーに「X にもう一度投稿」が出て録り直さずに試し直せる (クリップが消えない)

## 録画エンジン

単体テストではモックできない `MediaRecorder` / `captureStream()` の実挙動。

- [ ] **録画された動画の解像度が、再生中の画質と一致する。** `video.captureStream()` が返すのはデコード済みのフレームなので、解像度は `videoWidth/videoHeight` = **いま再生中の画質**になる。YouTube の設定で 360p に落としてから録り、できたクリップが 360p になることを確認する（再生中の「表示サイズ」ではなく「再生画質」に依存する点に注意）
- [ ] **720p 未満 (例: 360p) で再生中に録画を始めると、バーに「再生画質が低いままです (◯◯p)。画質を上げると綺麗に切り抜けます。録画の準備をしています…」が出る。** 警告だけで録画は止まらないこと
- [ ] 録画中もタブの音声が普通に聞こえる（captureStream は音声出力を奪わないはず）
- [ ] 録画された動画に音声が入っている
- [ ] `stream.getAudioTracks().length` を DevTools で確認し、`captureStream()` が実際に**音声トラックを含む**か確認する
- [ ] `MediaRecorder` が captureStream のストリーム（可変フレームレート・解像度）を**エンコードできる**か。tabCapture 由来とは特性が異なるため、コマ落ちやエンコード失敗が無いか長めのクリップでも確認する
- [ ] **`video.mediaKeys` が非 null になるタイミング**を確認する。仕様上 `setMediaKeys()` 前は null のままの実装もありうるため、「再生開始前」「再生開始後」で `assertRecordable` の判定結果に差がないか見る。**差がある場合、DRM 検出をすり抜ける経路が残る**
- [ ] **DRM 保護された動画（有料レンタルなど）で、録画ボタンを押した直後に「この動画は保護されているため録画できません」と出る**（60 秒待たされないこと）
- [ ] `onUnexpectedStop` の実機での発火経路を確認する (タブを非アクティブにしたときのブラウザ制限、`video` 要素が DOM から除去されたとき)。**発火したら OK の基準:** 録画中 (「録画中…」表示) のまま止まらず、OUT 到達を待たずにバーに「録画が中断されました」が出て、「再試行」ボタンが出ること
- [ ] 録画中に `MediaRecorder` を強制的にエラーにしたとき (例: DevTools でタブを閉じかける等)、OUT 到達を待たず**即座に** failed 表示に切り替わる
- [ ] 同じタブで連続して複数クリップを録画しても、タブが重くなる・音が乱れる等のリソース蓄積が起きない
- [ ] `recorder/started` の応答が届く前に録画が終わってしまうような操作 (OUT へ即到達する短いクリップ等) が発生しても、例外が投げられず失敗として処理される
- [ ] 生成された動画が MP4 / WebM いずれの環境でも実際に再生でき、1 秒ごとの chunk 分割によるコマ落ち・音ずれがない
- [ ] エラー発生と、録画の明示停止 (OUT 到達による自動停止、または録画終了直後に素早く「取り直し」を押した場合) のタイミングが近接したとき、表示される失敗理由が `InvalidStateError` のような内部例外名にすり替わっていない (ユーザー向けの文言のままである)。**「取り直し」は録画中は操作できない** (ボタン自体が表示されない) ため、encoding → preview に遷移した直後のタイミングを狙って確認する

- [ ] **DRM 保護コンテンツかつ広告再生中という組み合わせ**で、`drm-protected` が `ad-playing` より優先して表示されるか確認する

## X 添付

`X_SELECTORS` の候補配列やテンプレート展開など、実際の X の DOM でしか
検証できない項目。

- [ ] **本文が正しく入る。** `[yt-clip] 本文を execCommand で入力しました` または `[yt-clip] 本文を paste で入力しました` のどちらかが出ていること。**どちらも出ずに失敗する場合は、その旨を記録する**（3 つの対策すべてが効かなかったことになる）
      **どのコンソールを見るか:** この 2 つの `console.info` は x.com 側の content script (`src/content/x.ts`) が実行するので、**投稿タブ (x.com) のページコンソール** (DevTools を投稿タブで開く) に出る。service worker のコンソール (`chrome://extensions` → 「Service Worker」) に出るのは添付に失敗したときの `X への添付に失敗しました` だけなので、**SW コンソールだけを見て「3 つの対策がすべて効かなかった」と記録しないこと**
- [ ] 本文がファイルより先に入っている（添付で UI が作り直される前に入力されること）
- [ ] **最優先: タイトルが 1〜5 文字のクリップで paste 経路に落ちたとき、`x/attached` が正しく通知されるか。** 改行除去の修正が効いているかの実地検証。意図的に execCommand を失敗させる環境を用意できない場合は、コンソールログで `paste` 経路に落ちた実例を待つ
- [ ] Draft.js が空ブロックに**不可視文字 (U+200B 等) を挿入していないか** DevTools の Elements パネルでテキストノードを確認する。挿入されていると改行除去だけでは吸収できず、極端に短いタイトルで誤判定が残る
- [ ] 既存ドラフトが残った compose 画面で実行したとき、新しい本文が**追記される形**になっていないか (前のドラフトを上書きすること)
- [ ] **本文の改行が正しく反映されるか**。テンプレート既定値は `{title}` + 空行 +
      `{url}` でリテラル改行を含むため、X の contenteditable に貼り付けたときに
      1 行へ潰れていないかを重点確認する
- [ ] **「一部の画像/動画をアップロードできません。」が出ないこと。** X は `File.type` で対応形式を判定するが、`MediaRecorder` に渡す MIME は `video/mp4;codecs="avc1.640028,mp4a.40.2"` のようにコーデック指定を含み、**`File.type` はそのパラメータを保持する**。中身が正しい MP4 でもラベルだけで弾かれるため、添付する File と保存する Blob には**パラメータを落とした MIME** (`video/mp4`) を使っている。この表示が出たら、まず DevTools で `input.files[0].type` が `video/mp4` (9 文字) になっているか確認する
- [ ] `input.files` への代入後、X 側のプレビューサムネイルが表示される
- [ ] `X_SELECTORS.fileInput` / `X_SELECTORS.editor` の候補配列のうち何番目が
      実際にヒットしているか (`data-testid` が X 側の変更で変わっていないか)
      DevTools 等で確認する
- [ ] `/compose/` のパス判定が実際の投稿画面 URL と一致する (投稿ダイアログ
      (ポップアップ) と専用コンポーザ (`/compose/post` 等) の両方で確認する)
- [ ] **投稿ボタンが自動で押されていないこと** (自動添付後、送信は必ず手動)

## X が投稿後の変換で失敗したときの切り分け

**症状はどれも「問題が発生しました」か `Internal error[131]` しか出ない。**
どこが悪いのかを画面から読み取れないため、疑う順に手順を残す。実機で 9 本の
ファイルを X に投げて確定させた内容。

### 1. 映像トラックの表示変換行列 (最初にここを見る)

`<video>.captureStream()` のフレームは変換メタデータを持つため、Chromium の
muxer が行列を 1 要素ずつ書き写す分岐に入り、**最後の要素 `w` だけ書き忘れる**。
0 のままだと表示サイズの計算が 0 除算になり、X の変換が落ちる。

実機で確定済みの事実 (`src/content/display-matrix.ts` が対処している):

- 9 本のファイルで、X の成否がこの 1 要素と**完全に一致**した
- 失敗するファイルの**当該 4 バイトだけ**を直すと通る
- 成功するファイルの**同じ 4 バイトだけ**を壊すと落ちる

- [ ] できたクリップの `moov/trak/tkhd` の変換行列の **9 要素目が
      `0x40000000`** であること。0 なら `fixVideoDisplayMatrix` が効いていない。
      行列は tkhd の中身の先頭から version 0 で 40 バイト、version 1 で 52
      バイト目から 36 バイト。その 9 要素目 (+32) を見る

### 2. 音声のチャンネル数

X が受け付けるのは 2ch まで。YouTube は 5.1 / 7.1 を配信することがあり、
`captureStream()` はそのまま通す。8ch のまま録ると X の変換が落ちる。

**取得したトラックの `getSettings()` は `channelCount` を報告しない**ので、
何 ch かはファイルを調べるまで分からない。だから音声がある限り常にステレオへ
落としている (`buildRecordingStream`)。

- [ ] **5.1 / 7.1 音声の動画** (映画の予告編など) で録って添付できること
- [ ] コンソールに「音声をステレオに落とせませんでした」が**出ていない**こと。
      出ていたら AudioContext の経路が失敗し、8ch のまま録れている

### 3. H.264 のプロファイル

`avc1.42E01E` のように制約フラグ付きで頼んでも、実機のエンコーダは制約フラグを
立てず**素の Baseline** (profile_idc=66、制約フラグ 0x00) を出す。X はこれを
受け取った後の変換で失敗する。そのため `avc1.640028` (High) を指定している。

- [ ] できたクリップが **High (profile_idc=100)** であること

### 4. 本文の入れ直し

添付すると X が入力欄を作り直すことがあり、先に入れた本文が消える。

- [ ] 添付の直後 2 秒、コンソールに
      `[yt-clip] 添付で消えた本文を入れ直します` が出るか (出なくてもよい)
- [ ] 出た場合でも、本文が **1 通ぶんだけ**であること。URL やタイトルが
      2 回以上並んでいたら、入れ直しが積み上がっている

### 5. 準備完了の二重受信

- [ ] compose タブをリロードして `x/ready` を 2 回起こし、**本文が二重に
      入らない**こと。service worker のコンソールに「本文と動画は送信済みの
      ため、二度目の準備完了を無視しました」が出る

### 6. タイトルの取得元

- [ ] `YT_SELECTORS.title` の**何番目の候補**が当たっているかを DevTools で
      確認する。**要素に一致するだけでは足りない** (一致するが中身が空になる
      画面構成が実在し、本文からタイトルだけが消えた)
- [ ] タブのタイトル由来まで落ちた場合、SPA 遷移直後に**前の動画のタイトル**が
      混じっていないこと

## 設定

- [ ] バーの右端に ⚙ が出て、押すとパネルが開く。もう一度押すと閉じる
- [ ] ハッシュタグを入れて「保存」を押すと「保存しました」が出る
- [ ] 保存後、入力欄が**正規化された形** (`#` 付き・重複なし) に変わる
- [ ] `切り抜き　VTuber、神椿` のように全角空白と読点で区切っても分かれる
- [ ] 開き直すと保存した値が入っている
- [ ] **投稿本文の末尾にタグが入る**
- [ ] **タグを空にすると本文が URL で終わる** (空行が余らない)
- [ ] `posted` の状態でタグを変えて「X にもう一度投稿」すると、
      **録り直さずに新しいタグで投稿される**
- [ ] ダークとライトの両方でパネルが読める

## 録画の中止

- [ ] 録画中にバーへ「■ 中止」が出る
- [ ] 押すと `ready` に戻り、**範囲はそのまま残っている**
- [ ] そのまま「● 録画」で録り直せる
- [ ] **中止した分のファイルがダウンロードされていない**
- [ ] 書き出し中 (`encoding`) には中止が出ない。ここで止めると録り終えた
      ものを捨てることになる
- [ ] 中止しても動画の再生は止まらない (仕様)

## 投稿した後の使い回し

投稿が済むと `posted` になり、範囲とクリップを保持する。かつては `idle` に
戻しており、YouTube に戻ったとき IN/OUT が触れなくなっていた。

- [ ] 投稿まで通した後、YouTube のタブに戻ると**拡大バーがそのまま操作できる**
- [ ] バーに「X にもう一度投稿」が出ていて、**録り直さずに**同じクリップを
      投稿できる
- [ ] ハンドルを動かすと「● 録画」に変わる (`ready` へ戻り、クリップが外れる)。
      **古い範囲のクリップを持ち続けないことがここの要点**
- [ ] IN を押し直しても同じく `ready` へ戻る
- [ ] 添付に失敗した後 (`downloadable`) にも「X にもう一度投稿」が出る

## 自動保存

- [ ] 録画が終わるとブラウザのダウンロード先にファイルが増える
      (設定していなければ `~/Downloads`)
- [ ] ファイル名が X へ添付されるものと同じ (`yt-clip-<videoId>-<開始秒>s.mp4`)
- [ ] **投稿に失敗してもファイルは残っている**
- [ ] 取り直すたびにファイルが増える (仕様。消すのは利用者に委ねる)
- [ ] 保存できなかった場合でも**録画は失われない**。ページのコンソールに
      「録画を保存できませんでした」が出て、投稿の流れは続く

## 見た目

単体テストでは検証しない領域。

- [ ] **ダークテーマとライトテーマの両方**で、文字とボタンが読める
      (YouTube の設定 → デザイン で切り替えて両方見る)
- [ ] YouTube のボタンと並べて浮いていない
- [ ] 主操作 (録画 / 投稿) が塗りつぶし、それ以外が輪郭だけになっている
- [ ] 拡大バーに現在の再生位置が出て、再生に追従する
- [ ] 再生位置が窓の外に出たら目印が消える (端に貼り付かない)
- [ ] ハンドルが掴みやすい (細い芯の周りに余白があり、狙わなくても掴める)
- [ ] 選択範囲の外側が暗くなっていて、切り抜く場所が分かる
- [ ] 全画面表示やシアターモードに切り替えてもバーが壊れない

## popup

操作はページ内へ移した。popup は状態を映すだけ。

- [ ] popup に**ボタンが 1 つも無い**
- [ ] YouTube 以外のタブ (X の投稿画面など) で popup を開くと、
      いま何が起きているかが読める
- [ ] 録画中は残り時間が数えられる

## 全体フロー

複数コンポーネントをまたぐ状態遷移で、単体テストの範囲外になりやすい項目。

- [ ] 動画をまたいで IN を打ち直した後、バーの「● 録画」が誤って押せる状態
      (無効化漏れ) になっていないか
- [ ] **録画済みでプレビュー待ち (popup が「録画できました」) のときに IN を押すと、
      新しい範囲の ready に戻る。** spec §5.6 の「MARK_IN はどの状態からでも ready へ」
      どおりの意図した挙動だが、**前のクリップは状態から辿れなくなる** (自動保存でファイルは残る)
      (拡大バーのドラッグはこの状態では効かない。IN だけが通る)
- [ ] **録画中に対象の YouTube タブをリロードすると、popup が「録画が中断されました」(failed, `recording-aborted`) へ切り替わり「再試行」が押せる。** タブは生きているので `tabs.onRemoved` は発火せず、OUT を監視していた content script だけが消える経路。content script が読み込み時に状態を問い合わせて抜けさせる。**リロードしたページのバーにも同じ理由が出ること** (popup を開かなくても何が起きたか分かること)
- [ ] **録画中に別の YouTube タブを開いても (IN を押さなくても)、進行中の録画が中断されない。** 新しいタブの content script も読み込み時に状態を問い合わせるため、録画対象タブの判定を誤ると全録画が中断する
- [ ] **動画 A で IN を押した状態で別の動画 B をタブで開いたとき、B のバーに A の範囲が出ない。** B で「範囲を再生」を押しても、**B が A の開始位置へ飛ばされないこと** (B のバーは操作できず、ステータスも初期表示のままであること)
- [ ] 録画中に別の YouTube タブで IN を押しても、進行中の録画が中断・破損しない
- [ ] 録画中に popup の進捗表示 (残り秒数・プログレスバー) が実際に減っていく/動く
- [ ] ダウンロード後、「ダウンロード」「取り直し」ボタンが再び操作可能な状態に戻る
- [ ] MP4 非対応環境 (Linux Chrome 等) で WebM への退避が発生し、警告文言が出た
      上でダウンロードできる
