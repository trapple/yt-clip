# リリース前 手動確認チェックリスト

E2E (`npm run e2e`) は「拡張が読み込まれ、IN で範囲ができ、popup が録画できる
状態になる」という、**IN による範囲確定まで**しか自動化していない。実際の
録画・プレビュー・X への添付は、録画そのものが実時間かかる、耳や目で確認
するしかないもの、ログイン済みアカウントが要るものを含め、すべてこの
チェックリストで手動確認する。X への添付はログイン済みアカウントを必要と
するため、認証情報をテストに持たせない方針であえて自動化していない。

## 準備

1. `npm run build`
2. `chrome://extensions` を開き、デベロッパーモードを有効にする
3. 「パッケージ化されていない拡張機能を読み込む」で `dist/` を指定する
4. X にログインしておく

## 最初に確認すること (ここが通らないと以降は意味を持たない)

- [ ] **録画された動画に、コメント欄やプレイヤーの操作系が映っていない。** 動画の中身だけが録れていること
- [ ] **録画データが実際に保存されているか。** 1 本録ってプレビューが再生でき、DevTools の Application → IndexedDB → `yt-clip` → `clips` で Blob のサイズが妥当（数百 KB 以上）であること。**数バイト〜数十バイトなら転送が壊れている**
- [ ] **ツールバーを経由せず、YouTube のページから直接録画を開始できる。** 権限エラーが出ないこと
- [ ] **60 秒いっぱい・1080p のクリップが X に添付できるか。** 動画は base64 にして 2 回運ばれる（content → service worker → 投稿タブ）。大きいクリップだけ失敗する可能性がある。添付されたファイルのサイズが元と一致することも確認する。**失敗した場合は、無反応にならず YouTube ページのバーに「拡張への送信に失敗しました: …」が出て、popup が「録画が中断されました」(failed) へ抜けること**

## 通常フロー (MP4 対応環境)

### 範囲の指定

- [ ] **IN を押すまで拡大バーは操作できない。** バーはプレイヤーの下に薄く表示されているが、ハンドルをドラッグしても動かないこと (spec §5.3 のとおり、範囲が確定するまで操作させない)
- [ ] IN を押すと 15 秒の範囲ができ、拡大バーのハンドルが操作できるようになる
- [ ] YouTube のシークバーに、範囲が帯で重なって見える
- [ ] **1 時間以上の動画で、拡大バーのハンドルが秒単位で動かせる**
- [ ] ハンドルをドラッグすると、動画がその位置に追従する
- [ ] ハンドルが窓の端で止まり、それ以上動かない
- [ ] 範囲を 1 秒未満にしようとすると、そこで止まる
- [ ] 範囲を 60 秒より長くしようとすると、そこで止まる
- [ ] 「範囲を再生」で IN から OUT まで再生され、OUT で止まる
- [ ] 録画中は IN / OUT / ハンドルのいずれも操作できない
- [ ] **録画後 (popup が「録画できました」= preview) もハンドルが操作できない。** 状態機械はこの状態の範囲変更を拒むため、動かせてしまうと画面と状態が食い違う

### 録画〜投稿

- [ ] 「録画」を押すと開始位置へ移動し、そこから再生が始まる
- [ ] **クリップの冒頭が欠けていない** (IN で指定した位置から始まっている)
- [ ] OUT の位置で録画が止まり、末尾が伸びていない
- [ ] popup でクリップを再生して確認できる
- [ ] 「取り直し」で同じ範囲を録り直せる
- [ ] 「X に投稿」で投稿画面が開き、動画が添付される
- [ ] 本文にタイトルと開始秒つき URL が入っている
- [ ] **投稿ボタンが自動で押されていない**
- [ ] 実際に投稿して、X 上で動画がインライン再生される

## 拡大バーの操作 (詳細)

単体テストでは座標計算しか固めておらず、実際に触れるかどうかは実機でしか
分からない項目。

- [ ] `getBoundingClientRect().width <= 0` の**実発生条件** (シアターモード切替・フルスクリーン遷移) を再現し、そのときハンドルが窓の先頭へ飛ぶような見た目のジャンプが起きないか確認する
- [ ] `setPointerCapture` / `pointercancel` の実挙動 (ドラッグ中にタブを切り替える・システム通知が割り込む) を確認する。ドラッグが中途半端な状態で固まらないこと
- [ ] CSS 変数フォールバック色の**視認性** (ライト / ダーク双方の YouTube テーマで)。拡大バーのハンドルや選択範囲の色が背景に埋もれていないこと

## 制約の確認

- [ ] **OUT ボタンで範囲を確定させたとき、60 秒を超える／1 秒未満だとエラー文言が出て録画に進めない。** (例: IN の 70 秒後で OUT を押すと「クリップは 60 秒までです (現在 70 秒)」、IN の直後で OUT を押すと「クリップは 1 秒以上必要です」が出る。) **これは拡大バーのハンドルをドラッグしたときに黙って端で止まるクランプ挙動 (`clampHandle`) とは別の経路で、`onMarkOut` → `validateRange` (`src/content/youtube.ts` / `src/shared/time.ts`) を通る。ハンドル操作だけを確認してこの項目を省略しないこと**
- [ ] **X に未ログインの状態で「X に投稿」を押したとき、操作不能にならないか。** 投稿画面ではなくログイン画面が開くため添付は完了しない。popup に「取り直し」が出ていて、そこから抜けられること（service worker は数十秒で止まるため、時間切れによる自動退避は当てにできない）
- [ ] **投稿画面が開いた直後にそのタブを閉じたとき、操作不能にならないか。** 同じく popup から抜けられること
- [ ] 広告の再生中に録画しようとすると中断され、理由が表示される
- [ ] **録画中 (seeking / recording / encoding のいずれか) に対象の YouTube タブを閉じると、popup が「録画対象のタブが見つかりません」(failed, `tab-lost`) へ切り替わり「再試行」が押せる。** タブを閉じてから popup を開き直して確認する (`chrome.tabs.onRemoved` 経由。service worker は数十秒で止まるためタイマーによる退避は当てにできない)

## degraded path

- [ ] MP4 非対応の環境で「この環境では X に直接添付できません」と表示される
- [ ] その状態でもプレビューでき、WebM をダウンロードできる
- [ ] X の添付に失敗した場合、ダウンロードへ誘導される (クリップが消えない)

## 録画エンジン

単体テストではモックできない `MediaRecorder` / `captureStream()` の実挙動。

- [ ] **録画された動画の解像度が、再生中の画質と一致する。** `video.captureStream()` が返すのはデコード済みのフレームなので、解像度は `videoWidth/videoHeight` = **いま再生中の画質**になる。YouTube の設定で 360p に落としてから録り、できたクリップが 360p になることを確認する（再生中の「表示サイズ」ではなく「再生画質」に依存する点に注意）
- [ ] **720p 未満 (例: 360p) で再生中に録画を始めると、バーに「再生画質が低いままです (◯◯p)。画質を上げると綺麗に切り抜けます。録画の準備をしています…」が出る。** 警告だけで録画は止まらないこと
- [ ] 録画中もタブの音声が普通に聞こえる（captureStream は音声出力を奪わないはず）
- [ ] 録画された動画に音声が入っている
- [ ] `stream.getAudioTracks().length` を DevTools で確認し、`captureStream()` が実際に**音声トラックを含む**か確認する
- [ ] `MediaRecorder` が captureStream のストリーム（可変フレームレート・解像度）を**エンコードできる**か。tabCapture 由来とは特性が異なるため、コマ落ちやエンコード失敗が無いか長めのクリップでも確認する
- [ ] **`video.mediaKeys` が非 null になるタイミング**を確認する。仕様上 `setMediaKeys()` 前は null のままの実装もありうるため、「再生開始前」「再生開始後」で `assertRecordable` の判定結果に差がないか見る。**差がある場合、DRM 検出をすり抜ける経路が残る**
- [ ] **DRM 保護された動画（有料レンタルなど）で、録画ボタンを押した直後に「この動画は保護されているため録画できません」と出る**（60 秒待たされないこと）
- [ ] `onUnexpectedStop` の実機での発火経路を確認する (タブを非アクティブにしたときのブラウザ制限、`video` 要素が DOM から除去されたとき)。**発火したら OK の基準:** 録画中 (「録画中…」表示) のまま止まらず、OUT 到達を待たずに popup が「録画が中断されました」(failed, `recording-aborted`) へ切り替わり、「再試行」ボタンが出ること
- [ ] 録画中に `MediaRecorder` を強制的にエラーにしたとき (例: DevTools でタブを閉じかける等)、OUT 到達を待たず**即座に** failed 表示に切り替わる
- [ ] 同じタブで連続して複数クリップを録画しても、タブが重くなる・音が乱れる等のリソース蓄積が起きない
- [ ] `recorder/started` の応答が届く前に録画が終わってしまうような操作 (OUT へ即到達する短いクリップ等) が発生しても、例外が投げられず失敗として処理される
- [ ] 生成された動画が MP4 / WebM いずれの環境でも実際に再生でき、1 秒ごとの chunk 分割によるコマ落ち・音ずれがない
- [ ] エラー発生と、録画の明示停止 (OUT 到達による自動停止、または録画終了直後に素早く「取り直し」を押した場合) のタイミングが近接したとき、表示される失敗理由が `InvalidStateError` のような内部例外名にすり替わっていない (ユーザー向けの文言のままである)。**「取り直し」は録画中は操作できない** (ボタン自体が表示されない) ため、encoding → preview に遷移した直後のタイミングを狙って確認する

## YouTube UI

DOM の再描画やタイミングに依存し、単体テストの jsdom では再現しにくい項目。

- [ ] **動画 A で IN → SPA 遷移で動画 B へ → B で OUT** を押すと「動画が変わりました」
      と表示され、A と B をまたいだ誤った範囲では録画されない
- [ ] **動画 A で IN → SPA 遷移で動画 B へ → OUT を押さずに popup から録画**した場合も、
      「動画が変わりました」と出て失敗する (popup は「動画が切り替わりました」)。**B の映像を
      A のタイトル・URL つきで投稿してしまわないこと**
- [ ] **動画 A で IN → 動画 B へ遷移した時点で、YouTube のシークバーに重なっていた帯が消える**
      (A の位置の帯が B の画面に残らないこと)
- [ ] **SPA 遷移直後 (動画切り替え直後) に「範囲を再生」を連打、または直後に録画を開始したとき**、`video` 要素が一時的に取れない経路が実際に踏まれるかを確認する。踏まれた場合、無音のままハングせず理由が画面に表示されること
- [ ] **DRM 保護コンテンツかつ広告再生中という組み合わせ**で、`drm-protected` が `ad-playing` より優先して表示されるか確認する
- [ ] **`paintOverlay` が `.ytp-progress-bar` に `position: relative` が付いている前提で絶対配置している。** 実際に帯が YouTube のシークバーの正しい位置に出るか確認する
- [ ] **`seeking` から `recording` に移るまでの間、動画が本当に進んでいない** (IN の
      位置で止まったまま録画開始を待っている。コマ送り等で確認)
- [ ] シアターモード切替・ミニプレイヤー化などで DOM が再描画されても、IN/OUT バーが
      重複生成されず 1 つだけ存在し、押しても機能し続ける
- [ ] ミニプレイヤー化等で `video` 要素が一時的に取得できないとき、無音のまま
      ハングせず、理由が画面に表示される
- [ ] `requestVideoFrameCallback` による停止が OUT 秒に対してどの程度の誤差 (フレーム
      単位) で止まるかを実際に確認する

## X 添付

`X_SELECTORS` の候補配列やテンプレート展開など、実際の X の DOM でしか
検証できない項目。

- [ ] **本文が正しく入る。** `[yt-clip] 本文を execCommand で入力しました` または `[yt-clip] 本文を paste で入力しました` のどちらかが出ていること。**どちらも出ずに失敗する場合は、その旨を記録する**（3 つの対策すべてが効かなかったことになる）
      **どのコンソールを見るか:** この 2 つの `console.info` は x.com 側の content script (`src/content/x.ts`) が実行するので、**投稿タブ (x.com) のページコンソール** (DevTools を投稿タブで開く) に出る。service worker のコンソール (`chrome://extensions` → 「Service Worker」) に出るのは添付に失敗したときの `X への添付に失敗しました` だけなので、**SW コンソールだけを見て「3 つの対策がすべて効かなかった」と記録しないこと**
- [ ] 本文がファイルより先に入っている（添付で UI が作り直される前に入力されること）
- [ ] **最優先: タイトルが 1〜5 文字のクリップで paste 経路に落ちたとき、`x/attached` が正しく通知されるか。** 改行除去の修正が効いているかの実地検証。意図的に execCommand を失敗させる環境を用意できない場合は、コンソールログで `paste` 経路に落ちた実例を待つ
- [ ] Draft.js が空ブロックに**不可視文字 (U+200B 等) を挿入していないか** DevTools の Elements パネルでテキストノードを確認する。挿入されていると改行除去だけでは吸収できず、極端に短いタイトルで誤判定が残る
- [ ] 既存ドラフトが残った compose 画面で実行したとき、新しい本文が**追記される形**になっていないか (前のドラフトを上書きすること)
- [ ] **本文の改行が正しく反映されるか**。テンプレート既定値は `{title}` + 空行 +
      `{url}` でリテラル改行を含むため、X の contenteditable に貼り付けたときに
      1 行へ潰れていないかを重点確認する
- [ ] `input.files` への代入後、X 側のプレビューサムネイルが表示される
- [ ] `X_SELECTORS.fileInput` / `X_SELECTORS.editor` の候補配列のうち何番目が
      実際にヒットしているか (`data-testid` が X 側の変更で変わっていないか)
      DevTools 等で確認する
- [ ] `/compose/` のパス判定が実際の投稿画面 URL と一致する (投稿ダイアログ
      (ポップアップ) と専用コンポーザ (`/compose/post` 等) の両方で確認する)
- [ ] **投稿ボタンが自動で押されていないこと** (自動添付後、送信は必ず手動)

## 全体フロー

複数コンポーネントをまたぐ状態遷移で、単体テストの範囲外になりやすい項目。

- [ ] 動画をまたいで IN を打ち直した後、popup の「録画」ボタンが誤って押せる状態
      (無効化漏れ) になっていないか
- [ ] 録画中に別の YouTube タブで IN を押しても、進行中の録画が中断・破損しない

- [ ] ダウンロード後、「ダウンロード」「取り直し」ボタンが再び操作可能な状態に戻る
- [ ] MP4 非対応環境 (Linux Chrome 等) で WebM への退避が発生し、警告文言が出た
      上でダウンロードできる
